Research cutoff and live checks: November 8, 2026. Research only: no packages installed, published, or repeatedly downloaded. Sources below distinguish official definitions, observed API output, experiments reported by others, and unverified user diagnoses.

## What do npm downloads measure, and how current is the evidence?

### Takeaway

Downloads are distribution events, not unique users, installations, companies, or malicious executions. The historical official definition remains linked from the current public API documentation, but the historical open-source implementation explicitly is not the current production service.

### Cited Findings

- **Official, historical, July 22, 2014:** npm described counts as HTTP 200 responses serving package tarballs, including build servers, mirrors, and analysis robots. It explicitly recommended directional popularity interpretation, not user counts. Local cache reuse does not create another served tarball; ephemeral build environments can repeatedly fetch one. **Safe wording:** “npm's published explanation counts tarball deliveries, including automated traffic, rather than people.” **Does not show:** today's precise anti-abuse rules, bot fraction, or production implementation. Do not reuse its historical “50 downloads/day” signal threshold as a 2026 rule. [Original npm explanation](https://blog.npmjs.org/post/92574016600/numeric-precision-matters-how-npm-download-counts-work.html).
- **Official, currently available API documentation:** point gives an aggregate; range gives daily observations; endpoints return start/end boundaries, which are inclusive. Standard queries have an 18-month per-query limit, not an 18-month retention limit: earliest available date is January 10, 2015. Bulk queries support at most 128 packages and 365 days and exclude scoped packages. Per-version counts cover only the previous seven days. The document still links the 2014 explanation. **Safe wording:** “The API exposes package-level download totals, not deduplicated adoption telemetry.” **Does not show:** a complete current bot-detection specification. [Official API documentation](https://github.com/npm/registry/blob/main/docs/download-counts.md).
- **Important implementation correction:** npm/download-counts explicitly warns “This code base isn't what npm uses to serve download counts anymore.” Its source cannot verify current IP deduplication, filtering, collection, or backfill logic. Even the current API document's S3/map-reduce narrative should be attributed as documentation, not audited production architecture. [Original repository warning](https://github.com/npm/download-counts).
- **Current cache documentation:** npm's content-addressable cache stores HTTP request data and package-related data; cache misses/corruption can trigger refetch. **Safe wording:** “An install satisfied locally need not produce a registry tarball delivery.” Avoid “every install counts,” or “a package already installed will never count again.” [Official cache source](https://github.com/npm/cli/blob/latest/docs/lib/content/commands/npm-cache.md).
- **Mirror semantics:** the 2014 explanation says a mirror ordinarily fetches a version once, while its downstream cached deliveries are not new deliveries from npm. Metadata replication is distinct from fetching tarballs: the current crawler policy permits metadata replication and tarball inspection, and reserves IP/user-agent rate limiting for high-velocity website crawling. These website crawler controls are not proof of download-statistics deduplication. **Does not show:** that npm counts every end user's request to a third-party mirror, or that every mirror/CDN has the same upstream behavior. [Historical delivery explanation](https://blog.npmjs.org/post/92574016600/numeric-precision-matters-how-npm-download-counts-work.html); [current crawler policy](https://docs.npmjs.com/policies/crawlers/).
- **Concrete historical correction from a package-manager maintainer:** on March 9, 2021, Yarn maintainer Maël Nison corrected Richardson's article: Yarn switched in 2017 from Cloudflare caching to a CNAME to npm, so those Yarn downloads counted like npm downloads. Richardson acknowledged removing the erroneous Yarn passage. **Safe wording:** “Switching package-manager clients is not necessarily switching registries.” **Does not show:** a fresh 2026 audit of Yarn networking. [Nison's original comment](https://dev.to/andyrichardsonn/how-i-exploited-npm-downloads-and-why-you-shouldn-t-trust-them-4bme#comment-1c917); [author's correction](https://dev.to/andyrichardsonn/how-i-exploited-npm-downloads-and-why-you-shouldn-t-trust-them-4bme#comment-1c91f).
- **First-party maintainer account, December 2, 2025 displayed date:** Tanner Linsley describes TanStack's long-range queries being capped and explains library-level sums include core packages, adapters, addons, and legacy names, with potential double counting. **Safe wording:** “Summing a project's packages measures deliveries across those packages, not distinct customers or businesses.” **Caution:** the post's examples run through December 6 despite its December 2 date; its “27% missing” phrasing uses the smaller total as denominator, whereas the omitted share of 744M is about 21%. Its illustrative chunk loop shares inclusive boundary dates and should not be copied uncritically. Use the documented limit and aggregation caveat, not its numbers as independently verified measurements. [Original TanStack post](https://tanstack.com/blog/npm-stats-the-right-way).

### Inferences

- CI-heavy and human-driven packages can produce different downloads-per-user ratios; “all packages include CI, therefore comparisons remain valid” is not established. Stable methodology can help, but cache policies, release frequency, packaging, and missing days can still change trends. [Official definition](https://blog.npmjs.org/post/92574016600/numeric-precision-matters-how-npm-download-counts-work.html); [TanStack aggregation caveat](https://tanstack.com/blog/npm-stats-the-right-way).

### Gaps

- No complete, current official description of IP deduplication or all anti-abuse filtering was recovered. “npm does absolutely no filtering today” is too strong.
- PkgPulse is secondary commentary, not a measurement of the proportion of CI traffic. No credible universal correction factor from downloads to users or businesses was found.

## Are there concrete examples of manipulation or broken statistics?

### Takeaway

Yes, these are two separate issues with different evidence: reported experiments demonstrate manipulability, while read-only live API checks reproduce anomalous zero days in October 2026. Neither establishes that most downloads are fabricated, that package installation stopped, or that every weekly drop is a statistics failure.

### Cited Findings

- **Original historical experiment, March 9, 2021, edited March 16:** Andy Richardson reports inflating is-introspection-query to just under one million weekly downloads, with a public implementation and screenshots. His opening separately says over one million accumulated over the month. **Safe wording:** “A developer publicly demonstrated artificial download inflation in 2021.” **Does not show:** prevalence across npm or a current invariant that every repeated request is counted. His small Twitter poll is not representative adoption research. Do not reproduce the attack. [Original account](https://dev.to/andyrichardsonn/how-i-exploited-npm-downloads-and-why-you-shouldn-t-trust-them-4bme).
- **Original security-vendor research, May 28, 2026, Ron Popov/Tenable:** reports reproducing direct-tarball inflation to 17,000 downloads in about an hour; separately reports controlled publication experiments averaging 135.55, 141.91, and 158.16 downloads per version in three conditions. Reports ambar-src reaching about 50,000 downloads across 724 versions, tying the mechanism to a malicious campaign. **Safe wording:** “Tenable reported in May 2026 that repeated tarball fetches and version-triggered scanner traffic could inflate npm's public counters.” **Evidence status:** current-year first-party experimental report, not independently rerun here. **Does not show:** universal per-version bot baselines, no filtering of any kind, organic victim totals, or representative prevalence. Its remediation claim that short waiting periods eliminate risk should not be repeated as a guarantee. [Original research](https://www.tenable.com/blog/how-cyberattackers-inflate-malicious-package-npm-download-counts).
- **Academic analysis, arXiv v2 May 20, 2026:** Swierzy, Pohl, Ohm, and Meier analyze metric spoofability and report 71,710 sybil packages linked to teaRank manipulation. The download section says they found no information on restricted counting; that is not an audit proving no controls exist. The 71,710 figure is dependency-graph spam, not a measured number of download-spoofing packages. **Safe wording:** “Research on FOSS metrics documents how incentives can contaminate popularity and dependency signals.” **Does not show:** that 2% of downloads are fake, or that npm's download pipeline failed. [Original paper](https://arxiv.org/html/2505.05897v2).
- **Original community report, October 22, 2026:** ragojose reports zero counts for October 6 and 13-15 in xmcp, React, TypeScript, and Express. Followups include zuchka on October 22 and another package report on November 1. Thread remains Unanswered when fetched, with only a generic automated GitHub acknowledgement, not a substantive staff diagnosis or backfill commitment. **Safe wording:** “Users reported missing-looking days and requested a backfill and an explicit incomplete-data marker.” [Original discussion](https://github.com/orgs/community/discussions/210931); [automated response](https://github.com/orgs/community/discussions/210931#discussioncomment-19111709).
- **Independently reproduced read-only API observations, November 8, 2026:** React and TypeScript both still return zero on October 6, 14, and 15, surrounded by tens of millions on other days. Crucially, October 13 now returns **41,665,004 React** and **67,398,040 TypeScript** downloads, differing from the report's zeros. React October 12/16: 34,927,798/36,331,234. TypeScript October 12/16: 57,160,641/58,943,628. **Safe wording:** “As checked November 8, the API still returned anomalous zeros for React and TypeScript on three October dates; a fourth date cited in the complaint now had nonzero data.” **Does not show:** when/how October 13 changed, whether the nonzero total is complete, or a confirmed internal cause. [React raw API](https://api.npmjs.org/downloads/range/2026-10-05:2026-10-16/react); [TypeScript raw API](https://api.npmjs.org/downloads/range/2026-10-05:2026-10-16/typescript).
- **Official-response search boundary:** the official latest-50 incident feed, fetched November 8, spans June 2024 to November 2026. Searching incident titles and update bodies for statistics, download count, and metrics yielded no match. This is a bounded negative finding, not proof npm never acknowledged statistics problems anywhere. **Safe wording:** “I found no statistics-specific explanation in the checked status feed or substantive staff response in that thread.” [Official incident feed](https://status.npmjs.org/api/v2/incidents.json); [API's latest-50 scope](https://status.npmjs.org/api).

### Inferences

- Simultaneous zeros for very large independent packages strongly suggest incomplete statistics, rather than genuine simultaneous abandonment. Public API output alone does not reveal whether collection, aggregation, storage, or presentation is responsible. [React](https://api.npmjs.org/downloads/range/2026-10-05:2026-10-16/react); [TypeScript](https://api.npmjs.org/downloads/range/2026-10-05:2026-10-16/typescript).
- Counting real automated deliveries according to a disclosed definition is not itself broken telemetry. Unexpected missing days are a different reliability claim. Manipulation shows a weak trust signal, not proof the entire dataset is worthless. [Official definition](https://blog.npmjs.org/post/92574016600/numeric-precision-matters-how-npm-download-counts-work.html); [Tenable experiments](https://www.tenable.com/blog/how-cyberattackers-inflate-malicious-package-npm-download-counts).

### Gaps

- No statistics-specific official incident/postmortem or root cause was recovered. Do not label these zeros a confirmed registry outage or a confirmed permanent loss of raw logs.
- No representative trend evidence supports “npm weekly counts are routinely collapsing” or “most maintainers distrust npm metrics.”
- A community browser extension estimates missing counts. Its modeled replacements are not recovered official counts, despite its author's “real number” phrasing. See [extension announcement](https://github.com/orgs/community/discussions/210931#discussioncomment-19303668).
- Michael Arnaldi's exact original “isn't even capable of having reliable metrics and trusted publishing” status remains unrecovered. A fresh exact-phrase search did not locate it. The prior ledger's warning still stands: do not attach this wording to September 21 status 2101859863831753093, which contains a registry-migration threat instead. [Previously fetched actual migration post](https://x.com/MichaelArnaldi/status/2101859863831753093).

## Which broader maintainer frustrations have strong, bounded examples?

### Takeaway

Namespace governance and paid-service support offer concrete additional cases beyond publishing/security changes. They illustrate individual friction and design tradeoffs, not a survey of ecosystem sentiment or evidence that all support is ineffective.

### Cited Findings

- **Current official namespace policy:** first-come names, immediate active use expected; reserving names and selling/buying them prohibited. npm says it does not resolve squatting claims on demand or transfer names simply because someone wants them; formal trademark/IP process is the actionable route described. Paid organizations will not be considered squatted because private packages may exist. **Safe wording:** “npm's current policy sharply limits on-demand name reclamation.” **Does not show:** that inactivity proves squatting or that visible absence of public packages means a paid org is unused. [Official policy](https://docs.npmjs.com/policies/disputes/).
- **Original policy-frustration case, April 13, 2026:** calebcgates reports attempting to reclaim nark after failed outreach and says npm support offered only the trademark route. A May 31 reply by acdvs reports similar problems with an owner lacking contact details. Current official policy corroborates the broad constraint, not the private support correspondence or the user's “zero real downloads” assertion. **Safe wording:** “One developer documented being unable to reclaim a long-inactive name under npm's policy, while acknowledging the supply-chain risk of ownership transfers.” **Official response:** only generic bot acknowledgement visible; later replies are community commentary. **Does not show:** nobody uses nark, that transfer is safe, that all names are blocked, or a current reclamation campaign by a major maintainer. [Original case](https://github.com/orgs/community/discussions/192413); [independent user's followup](https://github.com/orgs/community/discussions/192413#discussioncomment-17125845).
- **Original billing/support case, September 24-25, 2026:** peaseBenjamin reports private-package E402 failures disrupting all their CI/CD pipelines, persisting after updating a card. September 25 followup says no response beyond automation for over a week and calls dependence on the ticket queue “incredibly disappointing.” Two other users report payment difficulties. **Safe wording:** “A paid-package user reported a week-long support wait while billing-related access failures blocked their pipelines.” **Evidence status:** users' reports, not independent account/bank inspection. **Official response:** none substantiated in visible thread. The marked answer is by community user Harshul1484; accepted status does not establish npm staff authorship or actual restoration. **Does not show:** a systemic billing outage, the bank/registry root cause, or continuing impact through November 8. [Original thread](https://github.com/orgs/community/discussions/208726); [author's specific support complaint](https://github.com/orgs/community/discussions/208726#discussioncomment-18600314); [community answer](https://github.com/orgs/community/discussions/208726#discussioncomment-18597906).
- **Useful maintainer distinction:** a dependency resolver/peer-dependency conflict is a client behavior unless evidence establishes registry metadata or delivery failure. Yarn's documented correction is a concrete reason not to collapse npm CLI, registry, mirrors, and website into one thing. A compatible replacement registry alone need not change lockfiles, lifecycle-script behavior, peer-dependency resolution, or funding economics. **Status:** architectural inference, not a newly verified bug case. [Yarn maintainer's correction](https://dev.to/andyrichardsonn/how-i-exploited-npm-downloads-and-why-you-shouldn-t-trust-them-4bme#comment-1c917); [current npm cache/fetching documentation](https://github.com/npm/cli/blob/latest/docs/lib/content/commands/npm-cache.md).

### Inferences

- Namespace stability versus reclaimability is a genuine tradeoff: transferring an old name can change who controls future releases installed by existing consumers. The complainant explicitly acknowledges that risk. Avoid presenting unrestricted reclamation as an unqualified security improvement. [Original complaint](https://github.com/orgs/community/discussions/192413).
- Download popularity cannot measure how many organizations can pay maintainers or a replacement registry. Summed package deliveries, duplicated dependencies, and repeated CI runs do not identify customers. [Official download definition](https://blog.npmjs.org/post/92574016600/numeric-precision-matters-how-npm-download-counts-work.html); [TanStack's aggregation acknowledgement](https://tanstack.com/blog/npm-stats-the-right-way).

### Gaps

- No representative survey, longitudinal complaint sample, or substantiated broad account-recovery/support SLA failure was established in this pass. Do not convert these selected threads into “maintainers are universally fed up.”
- Private support replies are quoted by users, not independently obtained from npm. No current resolution is verified for either case.
