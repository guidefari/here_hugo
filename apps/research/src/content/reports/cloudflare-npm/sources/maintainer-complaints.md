## What did Theo and Michael Arnaldi actually say, and what does it establish?

### Takeaway

Both have made explicit, verifiable threats to build or use another registry, not merely another package-manager CLI. The strongest technical account comes from fellow Effect maintainer Sebastian Lorenz, who documents publishing scans delaying a synchronized release for 22 hours and difficulty obtaining support. These establish substantial individual frustration, not a measured ecosystem-wide trend.

## What did GitHub/npm change, why, and what mitigation existed by the cutoff?

### Takeaway

GitHub is not simply ignoring npm: it has shipped substantial supply-chain defenses, session and token changes, staged publishing, multiple trusted publishers, and expanded tag permissions. The primary-source tension is that security controls can impose real delays and migration burden, especially for monorepos and unsupported CI providers.

### Cited Findings

#### Dated policy and response timeline

- **July 31, 2025:** GitHub's later roadmap identifies this as npm trusted publishing's general-availability date. It follows PyPI, RubyGems and crates.io, so OIDC itself is neither novel nor exclusive to npm or a hypothetical Cloudflare rival. The announcement URL is linked by the fetched roadmap; this research verified the date from that roadmap rather than separately fetching the GA post. [GitHub retrospective](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/); [GA announcement link](https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/).
- **September 14, 2025 incident; September 22 announcement:** GitHub says it was notified of Shai-Hulud on September 14, removed more than 500 compromised packages and blocked new uploads matching malware indicators. The attack used compromised maintainer accounts and malicious post-install scripts. GitHub then proposed required local-publish 2FA, shorter-lived granular tokens and broader trusted publishing. These are operator-reported mitigation counts, not independent incident statistics. [Primary announcement](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/).
- **September 23, 2025:** GitHub opened a feedback discussion. Wesley Todd welcomed much of the direction but wanted proof-of-presence 2FA in CI, explaining why OIDC was not a complete replacement for his workflow. Electron maintainer `MarshallOfSound` endorsed most security changes while requesting stronger identity binding, safer defaults and support for other CI systems. This is mixed feedback, not uniform maintainer opposition to security. [Discussion](https://github.com/orgs/community/discussions/174507); [Todd](https://github.com/orgs/community/discussions/174507#discussioncomment-14490094); [Electron account](https://github.com/orgs/community/discussions/174507#discussioncomment-14532227).
- **September 29, 2025:** GitHub specified a seven-day default and 90-day maximum for newly created write-enabled granular tokens, classic-token revocation and transition away from new TOTP setups. Existing granular tokens initially retained their current expirations. The post acknowledged rotation burden and incomplete trusted-publishing coverage. Its original proposed classic-token deadline was mid-November, not the eventual December completion date. [Announcement](https://github.blog/changelog/2025-09-29-strengthening-npm-security-important-changes-to-authentication-and-token-management/).
- **December 9, 2025:** GitHub announced actual permanent revocation of classic tokens. `npm login` switched to two-hour sessions, with 2FA for publishing; granular token create/list/revoke became available in the CLI; new packages gained default 2FA. GitHub also temporarily restored a legacy authentication API endpoint after November compatibility issues, especially affecting Yarn v1/v2. This is a concrete compatibility mitigation, not a dependency-resolution issue. [Completion announcement](https://github.blog/changelog/2025-12-09-npm-classic-tokens-revoked-session-based-auth-and-cli-token-management-now-available/).
- **May 22, 2026:** npm's September roadmap says staged publishing became generally available. The model separates CI upload from human approval with 2FA. Current docs verify that `npm stage publish` can be followed by review and `npm stage approve`, including website approval. [PM roadmap](https://github.com/orgs/community/discussions/208130); [Current staged-publishing docs](https://docs.npmjs.com/staged-publishing).
- **June 25 and September 9, 2026:** The PM roadmap describes preventive holds for high-impact accounts, later recovery-code security holds for all accounts. Successful recovery-code sign-in triggers a 72-hour hold on publishing and sensitive writes, while sign-in and consumption remain possible. These are security policies, not verified explanations of the named maintainers' incidents. Dates are verified from the roadmap, not separate fetches of both linked announcements. [PM roadmap](https://github.com/orgs/community/discussions/208130).
- **July 28, 2026:** The roadmap says publish-time malware scanning launched, with possible blocking or manual review. This supplies operator context for Lorenz's October complaint. GitHub explicitly says scanning is not a guarantee of detecting all malicious packages. [PM roadmap](https://github.com/orgs/community/discussions/208130); [Effect's observed impact](https://github.com/orgs/community/discussions/208130#discussioncomment-18860239).
- **July 31, 2026:** 2FA-bypass granular tokens lost the ability to create/delete tokens, change maintainers, package access or trusted publishing, and manage org/team membership and package grants. GitHub says a leaked bypass token could previously perform these sensitive actions. These now require interactive 2FA. The announcement targets **January 2027** for removing direct publishing with bypass tokens; do not describe this future restriction as already effective on November 8, 2026. [Primary announcement](https://github.blog/changelog/2026-07-31-restricting-npm-bypass-2fa-granular-access-tokens/).
- **September 3, 2026:** The PM roadmap says multiple trusted-publisher configurations shipped. The current docs allow up to 10 per package, superseding older complaints about a single workflow per package. [Roadmap](https://github.com/orgs/community/discussions/208130); [Current docs](https://docs.npmjs.com/trusted-publishers).
- **September 17, 2026 roadmap:** npm explicitly acknowledges that unsupported CI providers are a “real workflow gap”, that staging is not parity with native OIDC, and that token-backed staging still requires credentials and approval. It says no additional provider integrations are planned during the remainder of 2026; broader support and namespace-level OIDC are under consideration for 2027, not committed deliveries. Publishing plans and batch approval are rest-of-2026 priorities, not guaranteed release dates. [PM's original roadmap](https://github.com/orgs/community/discussions/208130).
- **September 30, 2026:** A dated release link in the roadmap discussion and current docs show opt-in OIDC support for `dist-tag` operations. Current docs require npm 11.21.0+ or 12.2.0+ and a separate “Allow npm dist-tag” permission. This addresses a specific blocker reported earlier in September, but does not make an entire monorepo release atomic. The date comes from the linked changelog and discussion; the capability itself is verified in fetched docs. [Release link](https://github.blog/changelog/2026-09-30-opt-in-dist-tag-permissions-for-npm-trusted-publishing/); [Current docs](https://docs.npmjs.com/trusted-publishers#managing-dist-tags-with-trusted-publishing); [Follow-up discussion](https://github.com/orgs/community/discussions/208130#discussioncomment-18712964).
- **October 29, 2026:** `postspectacular` still asks for an ETA on batch approval, calling individual approval infeasible for large monorepos. This shows an outstanding user need, not definitive proof that no release occurred anywhere by the cutoff. [Original](https://github.com/orgs/community/discussions/208130#discussioncomment-19264806).

#### Current capabilities and limitations verified in documentation

- Fetched trusted-publishing docs, last edited October 6, 2026, support GitHub-hosted Actions runners, GitLab.com shared runners and CircleCI cloud. Self-hosted runners remain unsupported. A package can have up to 10 trusted-publisher connections. A new configuration must perform its first successful publish within two days, binding to the repository's immutable identity; otherwise it expires. This also means older complaints about name-only identity binding should not be presented as unchanged current behavior. [Documentation](https://docs.npmjs.com/trusted-publishers).
- OIDC publishing does not solve private dependency installation authentication. The docs still recommend read-only granular tokens for private installs. Automatic provenance is limited to public packages built from public repositories through GitHub Actions or GitLab; CircleCI provenance is not supported. [Documentation](https://docs.npmjs.com/trusted-publishers).
- Current staged publishing explicitly supports a new-package placeholder `0.0.0-stage`, so claims that a manual first publish is always required are stale relative to these docs. The version under review remains unavailable until approval, but the placeholder itself is public. [Documentation](https://docs.npmjs.com/staged-publishing).
- npm advises stage-only OIDC permissions plus disallowing traditional publishing tokens for maximum security, adding a human 2FA approval even when CI uses OIDC. That is an explicit security/automation tradeoff, not a free UX improvement. [Documentation](https://docs.npmjs.com/trusted-publishers#why-this-matters).

### Inferences

- The strongest framing is “GitHub is hardening npm, but some maintainers argue the rollout and missing workflow support are becoming operational liabilities,” rather than “npm has done nothing.” Both halves have direct primary support. [GitHub changes](https://github.com/orgs/community/discussions/208130); [Effect experience](https://github.com/orgs/community/discussions/208130#discussioncomment-18860239).
- Avoid bundling registry authentication changes with npm v12's dependency lifecycle-script defaults. The roadmap discusses both, but they affect different layers. The article's displacement question concerns registry ownership, publishing authorization and distribution, not simply switching npm to Bun or pnpm. [Roadmap](https://github.com/orgs/community/discussions/208130); [Theo's distinction](https://x.com/theo/status/2110970338511405078).

### Gaps

- No verification that the named September/October release incidents received a lasting fix, SLA, incident postmortem or compensation.
- No systematic support-response-time measurements or independently measured scanning-delay distribution.
- The original 2025 announcements are marked “Retired” on the current GitHub blog. They are useful historical records, not a substitute for current documentation.
- Several dated entries above are explicitly sourced through the PM's retrospective roadmap rather than separately fetched launch posts. Recheck linked originals before using a fine-grained implementation claim unsupported by current docs.

## Would a Cloudflare-operated registry solve these problems, and is frustration demonstrably growing?

### Takeaway

The evidence supports an opening for a registry with better publishing operations, support and interoperable auth. It does not establish that Cloudflare is uniquely capable of exploiting it, that CDN infrastructure fixes maintainer workflows, or that frustration is rising at a measurable rate.

### Cited Findings

- Arnaldi's proposed destination is an Effect-controlled registry, not Cloudflare; Theo's posts discuss building a better registry without naming Cloudflare. These are primary expressions of demand for alternatives, not endorsements of this article's particular candidate. [Arnaldi](https://x.com/MichaelArnaldi/status/2101859863831753093); [Theo](https://x.com/theo/status/2110937874384511156).
- The documented Effect pain occurs **before a synchronized release is fully available**, during scanning/validation and publishing. A faster tarball CDN alone would not change those authorization, review or release-coordination decisions. The underlying distinction follows directly from the maintainer account and staged-publishing model. [Effect account](https://github.com/orgs/community/discussions/208130#discussioncomment-18860239); [Publishing model](https://docs.npmjs.com/staged-publishing).
- npm's PM explicitly states that onboarding an OIDC provider requires evaluating identity claims and security controls, not merely recognizing a token. A competitor also faces this security-policy burden. [Roadmap](https://github.com/orgs/community/discussions/208130).
- Some early complaints have already received partial mitigations: CLI OIDC setup, multiple trusted publishers, staged new-package creation and OIDC tag operations. Any opportunity analysis must compare against the contemporary product, not exclusively its 2025 launch limitations. [PM CLI reply](https://github.com/orgs/community/discussions/208130#discussioncomment-18489512); [Current OIDC docs](https://docs.npmjs.com/trusted-publishers); [Current staging docs](https://docs.npmjs.com/staged-publishing).

### Inferences

- **Could improve, if actually built:** clear publish/scan status and diagnostics, predictable review turnaround, supported monorepo release transactions or coherent promotion, documented escalation, org-level OIDC setup, and broader CI interoperability. These are product requirements inferred from complaints, not capabilities established for Cloudflare. [Effect complaint](https://github.com/orgs/community/discussions/208130#discussioncomment-18860239); [OTP/configuration complaint](https://github.com/orgs/community/discussions/208130#discussioncomment-18489235); [Opaque rejection report](https://github.com/orgs/community/discussions/208130#discussioncomment-18580786).
- **Would not automatically solve:** compromised build workflows, malicious release contents, maintainer account recovery, secure ownership transfers, token rotation and security-versus-unattended-publishing tradeoffs. Changing operators relocates those design responsibilities. The incumbent's documented attacks, policy rationale and provider requirements explain why these cannot be solved by distribution infrastructure alone. [GitHub attack response](https://github.blog/security/supply-chain-security/our-plan-for-a-more-secure-npm-supply-chain/); [Bypass-token attack surface](https://github.blog/changelog/2026-07-31-restricting-npm-bypass-2fa-granular-access-tokens/); [Provider roadmap](https://github.com/orgs/community/discussions/208130).
- **Counterfactual caution:** avoiding scanning delays by eliminating scanning might improve release speed while discarding a security defense. The article should ask how an alternative preserves security while improving workflow, rather than assuming every source of friction is needless. GitHub itself describes scanning as a defense with limitations, while Lorenz disputes its operational rollout. [Roadmap](https://github.com/orgs/community/discussions/208130); [Effect account](https://github.com/orgs/community/discussions/208130#discussioncomment-18860239).
- **Trend wording:** the material documents repeated complaints, including an Effect maintainer saying they were repeatedly bitten over recent months, and two high-profile threats in September and October 2026. It does not quantify prevalence or change over time. “Growing frustration” should be presented as the article's question or impression, not a research finding. [Repeated Effect experience](https://github.com/orgs/community/discussions/208130#discussioncomment-18860239); [Arnaldi](https://x.com/MichaelArnaldi/status/2101859863831753093); [Theo](https://x.com/theo/status/2110937542141059454).

### Gaps

- No source in this assigned evidence establishes Cloudflare's own registry plans, unique technical advantages, operating economics, compatibility, governance or security-support capabilities. Those require separate infrastructure and competitive research.
- No maintainer sentiment time series, representative survey, npm churn metric or evidence of completed mass migration was found.
- No verified evidence here that changing registry operator alone resolves npm account recovery or org administration better, nor that maintainers would accept the migration and trust costs.
